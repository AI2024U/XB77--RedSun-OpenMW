## Proposed signing rationale

We seek a verifiable link between public open-source code, a reviewed automated build, and the distributed Windows executables. This can protect users against substituted downloads and provide reliable publisher identity without asking players to weaken Windows security.

## Eligibility obstacles to resolve first

SignPath Foundation's conditions for signing a **modified upstream program** explicitly require (a) upstream signed releases, (b) a **visible upstream fork**, and (c) signing releases based on the upstream branches normally signed. This independent repository is **not** a recognized fork, and upstream signing eligibility has **not been established**. The policy also requires the project to have already released a downloadable program in the same form, maintainers, documented code review/signing roles, multi-factor authentication, privacy policies and a manually approved signing request.

- [ ] Independently confirm OpenMW officially signs its Windows binary releases.
- [ ] Ask SignPath whether this custom distribution is eligible and what visible-fork arrangement would comply.
- [ ] Publish complete corresponding source, not merely links or private source archives.
- [ ] Release a thoroughly audited unsigned public build.
- [ ] Verify MFA, maintainer roles, public CI integrity and required metadata restrictions.
- [ ] Submit only verified facts, without personal contact information in the public repository.

SignPath may decline or may allow **only the separately authored custom wizard**, depending on its rules. Do not assume it will sign modified OpenMW binaries.
